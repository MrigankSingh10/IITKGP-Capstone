# Blind fresh relevance review

Open [the review CSV](../evaluation/relevance_fresh_review.csv). It contains questions and empty judgment fields, with no proposed pages, retrieval rankings, answers or model verdicts. Do not consult earlier retrieval results, assisted labels or generated answers while judging. These are proposed questions, not a frozen benchmark. The question author inspected the corpus when writing them; reviewer judgments must be independent. Do not tune the retrieval system against this set.

For each question, examine original corpus PDFs and identify every page that provides relevant evidence, including pages needed for separate parts and linked instruments where appropriate. Use the actual source and 1-based PDF page, not a printed page number. The searchable registry `data/processed/accepted_ocr/pages.jsonl` maps `page_id`, source title and original filename; `data/raw/<source_pdf_id>.pdf` contains the source. Search documents independently; do not use system-ranked results to decide labels. For OCR pages, check the original scan and flag transcription uncertainty. For Hindi and bilingual cases, a reviewer competent in both languages should check the original language; preserve distinct IDs for separate PDFs. The source conflict question requires recording the original wording and the statutory source, without silently resolving the discrepancy. Judgments are document relevance, not legal applicability.

In `relevant_page_ids`, enter full IDs separated by semicolons, for example `FULL_SHA256:page_0001;FULL_SHA256:page_0002`. Enter reviewer name and `approved` in `review_status` only after checking the question and page IDs. Record ambiguities and scope limitations in `notes`. If no indexed evidence is available, or the question is ambiguous, leave unapproved and describe it in notes; do not create a guessed label. These rows need adjudication or exclusion before freeze. Another qualified reviewer should resolve disagreements independently and record the decision. No assumption of exhaustive labels should be made if the corpus was not comprehensively checked.

Evidence-missing evaluation is separate from relevance recall: document the missing source and expected escalation after independent review; do not insert empty labels into the relevance metric. The separate [evidence-missing review sheet](../evaluation/relevance_evidence_missing_review.csv) contains two proposed cases; reviewers must confirm what evidence is missing and the expected handling. It is not scored by the relevance runner.

After every row is signed off, freeze and evaluate with:

```bash
.venv/bin/python scripts/evaluate_relevance_fresh.py freeze
.venv/bin/python scripts/embed_relevance_frozen.py --base-url "$EMBEDDING_BASE_URL" --model "$EMBEDDING_MODEL" --key-file "$EMBEDDING_KEY_FILE" --ca-file "$EMBEDDING_CA_FILE"
.venv/bin/python scripts/evaluate_relevance_fresh.py score --model "$EMBEDDING_MODEL"
```

The embedding step makes network calls only after checksum-verified freeze; no query vectors are generated by the scorer. Use the same embedding model as the corpus cache. Check corpus vector coverage in the output; sparse and non-Latin chunks may be absent. The scorer reports hit@10 (at least one relevant page), macro page recall@10, MRR@10 (first relevant page), query-language slices and mean local search time for BM25, dense, hybrid and hybrid plus lexical rerank at both chunk sizes. Local time includes ranking and per-query index setup; it excludes embedding, network and other end-to-end costs. End-to-end latency is not measured. Scores treat unlisted pages as non-relevant, so incomplete review can understate performance. Small language slices are descriptive only. Freeze and output are new artifacts; never overwrite frozen cases. The checksum detects accidental changes, not malicious edits.
